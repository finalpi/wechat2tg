# 群名、头像同步与 Telegram 限流

`FloodWaitError` / `code: 420` 表示 Telegram 要求暂停相关操作。日志里的 `seconds: 690` 是 11 分 30 秒；`channels.EditTitle` 是修改超级群标题，不是发送聊天消息。判断消息是否发送成功，应看同一条微信消息 ID 对应的发送结果，不能把群名更新失败当作消息发送失败。

## v6.0.19 的修复

此前启动同步会给所有绑定设置相同的 500ms 定时器，实际同时发起更新。头像遇到限流后只打印“等待”，既没有共享冷却时间，又会继续修改群名；多个服务实例也会继续请求，产生重复警告和错误堆栈。

现在：

- 同一个 Telegram User Client 的所有群名/头像更新共享串行队列；重复的进行中请求合并，不同客户端互不阻塞。
- 启动同步等待当前群更新完成，再间隔 500ms 处理下一个群，不再同时启动所有任务。
- 头像或群名遇到 FloodWait，都记录 Telegram 要求的冷却时间；头像限流后不再继续修改群名。没有有效等待秒数时，保守暂停 60 秒。
- 冷却期间跳过元数据更新，不下载/上传头像，不修改群名，不为每个跳过的群重复打印日志。每次触发新的冷却只记录一条警告。
- 这里只暂停群名/头像维护，不增加消息发送重试，不在消息转发队列中等待这段冷却。
- 头像和群名分别只在确认成功后记入本地。头像成功、群名失败时保留已成功的头像记录；失败的头像不会假装更新成功。

这不能取消 Telegram 的限制，也不保证其他操作不会限流。客户端重启不会清除 Telegram 服务端的等待要求；本地冷却仅保存在当前进程中。

## 如何处理

1. 暂时不要反复点击 `/update` 或重启应用尝试绕过限制。
2. 可以在 Bot `/settings` 中关闭“启动时同步群组信息”，减少重启后的自动维护请求；普通消息转发不依赖这个开关。
3. 等待服务端要求的时间后，在需要更新的已绑定群中执行 `/update`，或等后续同步触发。冷却期间跳过的元数据任务不会自动全部重放。
4. 若 `sendMessage`、发送媒体等操作也出现限流，需要单独检查对应操作；本修复不声称能绕过账号或 Telegram 的全局限制。
