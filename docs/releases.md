## 开发预览：v6.0.42-dev.25（非稳定版）

- 修复 Telegram 位置转发到已绑定的微信会话时无消息的问题。微信端按原生位置卡片发送；地点名称和地址保留，实时位置仅发送首次收到的坐标。

## 开发预览：v6.0.42-dev.24（非稳定版）

- 修复断网期间 MTProto 送达回查（`getMessages`）无超时导致单会话 outbox 永久卡在 `sending` 状态、阻塞后续所有消息转发的死锁问题：为文本回查（10s）和大文件回查（15s）加上硬超时保护。

## 开发预览：v6.0.42-dev.23（非稳定版）

- 大文件 MTProto 上传提升为 4 并发分片工作池，同时在领取下一片前继续检测并让路给正在发送的普通 Telegram 消息，兼顾上传吞吐与聊天消息不卡顿。

## 开发预览：v6.0.42-dev.22（非稳定版）

- 彻底解决大文件上传期间微信→TG 消息卡顿与丢消息问题：
  - 大文件 MTProto 上传改为按 512 KiB 分片串行上传，并在每片发送前自动让路给正在发送的普通 Telegram 消息，不再打满上行带宽。
  - 普通文本消息发送超时时自动通过 MTProto 回查目标会话最近消息：若已送达则补回回执，若确认未送达则自动转为可重试由 outbox 退避重发，避免静默落入 `unknown` 丢消息。

## 开发预览：v6.0.42-dev.21（非稳定版）

- 将 MTProto 大文件上传并发调整为 `workers: 2`，并将 Bot API 文本消息发送超时从 30 秒放宽到 60 秒，减轻大文件上传期间的上行拥塞并避免普通文本消息因短时排队被误判超时丢弃。

## 当前 Bot 正式版：v6.0.41

相较上一正式版 **v6.0.40**，本版汇总 `v6.0.41-dev.1`～`dev.17` 的改进，并包含最后的红包极简交互修正。

### 主要变化

- **静态表情不再冒充 GIF**：按实际内容及帧数识别 PNG、JPEG、WebP 和单帧 GIF，以图片发送；真正多帧动图保留动画。覆盖实时转发、手动同步和重试下载，保留说明、按钮、Topic 与回复关系，不改写归档、不自动替换旧消息。
- **红包只保留一条消息**：沿用原封面样式，正文只留祝福语，下方一个「拆红包」按钮。主人点击后后台随机等待 1～3 秒，无二次确认消息、进度消息或额外结果消息；结果出来只编辑一次原按钮，直接显示「已领取 ¥1.23」或失败。仅确认未派发且授权仍有效的失败提供重试，结果未知不重领。**金额在原按钮上，对能看到该消息的人可见。** WebUI 仍需确认。旧红包的封面字段与照片按钮缺失问题也已修复，详见 [红包说明](red-packets.md)。
- **WebUI 聊天体验**：同日连续同一发送者不再因时间间隔被拆组；富文本输入、光标位置的 @ 成员选择、微信表情选择与行内显示、发送后焦点恢复；图片可缩放、旋转、移动和下载，视频先加载缩略图再主动播放，引用消息可定位并返回最新位置。

## 版本编号与通道

以下 Docker 规则只适用于 bot 仓库 `finalpi/wechat2tg`；不修改 `finalpi/wx2tg-server` 的镜像命名和版本规则。

| 类型 | 完整 Git 标签 | bot Docker 标签 | bot 滚动别名 |
| --- | --- | --- | --- |
| 稳定版 | `v6.X.Y` | `v6.X.Y` | `v6`、`latest` |
| 开发版 | `v6.X.Y-dev.N` | `v6.X.Y-dev.N` | `v6-dev` |
| 手动快照 | 无，从 `v6` 分支手动构建 | `v6-dev-<提交短 SHA>` | 无，不更新稳定或开发滚动别名 |

例如：`v6.0.13-dev.1` → `v6.0.13-dev.2` → 验收后 `v6.0.13`；后续再进入 `v6.0.14-dev.1`。`N` 从 1 开始，不允许前导零。npm / `package.json` / `VERSION` 去掉前面的 `v`；Git 标签和 bot Docker 完整版本均保留 `v`，校验要求完整的 `v` + `VERSION`。

- Bot、puppet、server 可独立递增版本并创建各自 tag，只要求同为 `v6`；无需为了 Bot 更新而重发 SDK/server。Bot 仍精确固定实际使用的 puppet 版本（不用 `^` / `~`），锁文件和制品必须与该依赖版本一致。这个校验仅检查版本规则，不代替具体接口兼容性验收。
- **开发 tag 永远不更新稳定别名。** server 的开发 GitHub Release 标记为 prerelease，不抢占 stable latest。
- 完整版本 tag 不移动、不覆盖；重发修复使用新的 `dev.N` 或正式版本号。
- 历史 `wx2tg-v3`、`860-v3`、`875`、`v51.*`、裸 `v6` / `v7` 等保留，不重写历史。旧 Git tag `v6` 不是滚动发行入口；脚本使用 `refs/heads/v6` 和 `refs/tags/v6.X.Y…` 避免歧义。
- bot 发布到 `finalpi/wechat2tg`，使用完整版本标签（含开头的 `v`）。正式版同时更新 `v6` 和 `latest`，开发版更新 `v6-dev`。旧 `finalpi/wechat2tg-v3` 仓库及其所有镜像、标签保留。

## amd64 / arm64 独立发布

bot 工作流先验证版本并运行测试，再并行执行两个互不等待的原生构建：

- `Build amd64`：`ubuntu-24.04`，发布 `v6.0.41-amd64`。
- `Build arm64`：`ubuntu-24.04-arm`，发布 `v6.0.41-arm64`。
- 两种架构分别使用 GHA 构建缓存；`fail-fast=false`，ARM 失败不会取消已成功的 amd64。
- 两边都成功后，才合并通用多架构标签 `v6.0.41` 和对应通道别名。

想尽早部署 amd64 时，使用 `finalpi/wechat2tg:v6.0.41-amd64`，或稳定滚动别名 `v6-amd64`。ARM 对应 `v6.0.41-arm64` / `v6-arm64`。正式 Git tag `v6.0.41` 发布 Docker `v6.0.41`、`v6.0.41-amd64` 和 `v6.0.41-arm64`，稳定别名为 `v6-amd64` / `v6-arm64`，合并后同时更新 `v6` 和 `latest`。手动快照只发布 `v6-dev-<短 SHA>-amd64` / `v6-dev-<短 SHA>-arm64` 和合并的 `v6-dev-<短 SHA>`，不更新任何滚动别名。

因此不必等整个工作流结束才能更新 amd64；部署端应核对目标提交和 **`Build amd64` 成功**。通用标签仍等待 ARM，保留正确的多架构内容，不会先用 amd64 覆盖掉 ARM。具体耗时受原生依赖编译、缓存和 runner 排队影响，不承诺固定 30 分钟。server 有原生库限制，仍只构建 amd64，不伪装支持 ARM。
