# 微信登录等待全量联系人同步（dev.4 修复）

## 现象与根因

用户在 Bot `v6.0.40-dev.3` 提供的日志中，SDK 完成数据库初始化后，顺序处理了 449 个联系人（439 成功、10 失败），到约一分钟后才出现 Bot 的 `WechatBot - DataSource initialized`。后续 Telegram 群资料更新的 `CHAT_ID_INVALID` 是另一个阶段的错误，不是这次联系人等待的原因。

调用链：

```text
WeChatClient.login()
  → SDK WxBot.start()
    → loginSuccess()
      → await fetchAllContacts()   ← 等待每页的全部详情
      → 启动消息接收 / login 事件 / 心跳
    → 分发启动 Sync 的积压消息
  → Bot 初始化 puppet.db 的独立读取连接
```

SDK `6.0.17` 正确补齐了联系人详情的等待和异常捕获，但全量任务仍被放在登录关键路径上。之前的单批联系人测试证明了并发上限和错误隔离，却没有断言「目录保持未完成时登录和消息接收必须先就绪」。PWA / WebUI 布局没有改变这条 SDK 调用链。

## 修复

- 将全量目录工作从 `loginSuccess()` 的等待链移到受管理的后台任务；登录、接收、心跳和已取得的启动消息先就绪。
- 每页仍最多 4 个详情请求，等待本页结束再翻页；不恢复未捕获的 `forEach(async ...)`，不提高并发上限。
- 退出 / 重新登录后，旧任务不再启动剩余详情、继续翻页或发出完成通知；新目录任务等待旧在途请求结束，总并发仍受限。
- 清缓存、扫码切换账号之前等待旧在途写入结束，避免旧任务在清空后重新写入。这个等待只涉及已经发出的旧请求，不继续处理剩余联系人。
- 联系人接口失败保留已有目录，不主动登出。会话失效仍交由原消息 Sync 检测和单次恢复逻辑处理。
- 当前目录轮次结束时发出 `contacts-updated`（后续分页失败而留下部分更新也会通知）；Bot 只刷新 WebUI 联系人，不重复登录或重跑群维护。
- 对显式需要初次目录的 SDK 使用方提供 `waitForContactSync()`。它等待当前轮次，不保证失败项已经成功，不额外启动同步。

注意：`start()` / `loginTwice()` 返回不再意味着全量联系人目录完成。网络确认、自身资料查询及必要初始化仍可能等待，不能承诺实际微信网络上的固定登录秒数。

## 回归证据

SDK：

```sh
node --test test/login-contact-startup.test.cjs test/contact-sync.test.cjs test/callback.test.cjs
npm test
```

- 修复前，保持联系人请求未完成时，真实 SDK 启动流程的 `ready=false`、登录事件为空、心跳次数为 0、消息接收未启动；polling 和 callback 均失败。
- 修复后覆盖启动恢复、二次登录、扫码登录 × polling / callback；联系人详情仍等待时，接收与登录已就绪，已取得的启动消息未丢弃。
- 覆盖分页失败、请求拒绝、失效提示、旧会话延迟响应、退出时序、跨任务并发上限及清缓存顺序。
- SDK 全部 197 项测试通过。

Bot：

```sh
npm run build
node --test test/wechat-startup-directory.test.cjs test/wechat-login.test.cjs test/release.test.cjs
```

集成测试运行真实 Bot 的 `login/init` 方法、实际安装的 SDK 制品和两个真实 TypeORM/SQLite 连接；仅隔离外部服务和可控的联系人等待。验证目录未完成时 Bot 已在线、镜像连接已开始初始化、旧缓存仍可读；后台写入后镜像读到新联系人，且 WebUI 收到目录通知。

同一集成测试通过进程级模块解析重定向加载**原始 `6.0.17` 制品**时失败（`initialized=false`、`online` 未就绪），加载新本地制品时通过；未改写旧包或安装目录来伪造结果。

Bot 构建和全部 517 项测试（串行）通过，消息、配置、Mini App、自动化、PWA 五组浏览器回归通过。浏览器中离屏历史行的断言改为确认挂载 / 移除，不把 `content-visibility` 未绘制的离屏内容误判为 SSE 丢消息。

所有数据为临时合成数据，没有登录真实账号、发送消息或操作远端服务。
