# Telegram 发送失败后的保留与恢复

## 已确认的代码问题与调查边界

旧 `MessageBufferService` 只保存内存状态，默认重试 3 次、5 分钟清理。所谓保存失败消息实际仅写日志；部分结果未知的请求又被转成成功以结束重试，随后移出缓冲。即使配置无限重试，也会在旧 TTL 的 6 倍后清理。因此网络恢复不代表旧消息会补发。

这些是代码中可复现的问题，不等于已读取用户故障时的服务器日志，也不据此断言那一次具体中断的网络原因。Telegram `getUpdates` 接收健康监测和这里的 WeChat → Telegram 发送恢复是两个独立链路。

## 当前实现

- 进入 Telegram 转发队列的消息先写入私有 SQLite `storage/db/telegram-outbox.db`（含 WAL）。媒体字节与文本元数据一并保存；成功入队不是成功送达。
- 以 Telegram Bot 身份、微信账号、会话、微信消息 ID 和类型去重，记录原目标群 / Topic。只有当前登录账号匹配才调度；真正调用 Telegram 前再次检查。不要让两个实例共享同一份可写 storage。
- 明确未建立连接的错误（例如 DNS、连接拒绝、不可达、带 `syscall=connect` 的连接超时）和明确的 429 持续退避，不受普通错误 3 次重试上限影响。指数等待最长 5 分钟，并至少等待服务端 `retry_after`。
- 通用超时、连接重置、服务端 5xx 等不能证明 Telegram 没有收到消息，保留为 `unknown`，不冒充已发送，也不自动整条重发。普通错误用尽配置的重试次数后保留为 `failed`，而不是丢弃。
- 重启时尚未开始请求的任务恢复排队；已经进入请求阶段的任务保守转为 `unknown`。不保证 Bot API 在“服务端收到但客户端没收到确认”情况下恰好发送一次。
- 长文本冻结第一次渲染的分片和目标，逐片持久记录已确认的 Telegram ID。明确未送达的后续分片失败时，从未确认部分恢复；不会重新发送已经确认的前缀。写入本地确认记录失败时保留未知，不因为数据库写失败重复发送。
- 文字和媒体有独立并发预算，仍进入原来的会话发送通道并使用原有限流器；不修改上传超时、代理、协议服务器或公众号路由。待发原消息被微信撤回时不在恢复后重新发出；已在途请求仍需按实际结果处理。
- 未送达记录不按 TTL 删除。`MESSAGE_BUFFER_EXPIRE_TIME` 仅用于清理已完成记录，至少保留 7 天作去重。关闭 WebUI 不关闭持久队列，但未知结果的人工核对更方便通过 WebUI 完成。

## 如何处理旧的漏发消息

1. 在 Telegram 核对是否已经收到，特别是超时、连接重置或长文本只收到一部分的情况。
2. 在 WebUI 对应会话查找那段时间的记录。消息正文、SDK 缓存和服务端归档是否仍在，决定能否找回。
3. 自动队列中的消息不能再并行手动同步；失败 / 未知记录可在核对后使用“同步 Telegram”。未知状态会要求确认重复发送风险。该操作不会向微信重发。
4. 旧版本已经清理、且其他存储也没有保留的内容无法凭空恢复。本改动不自动批量重发历史记录，不把所有 `tgBotMsgId=0` 的旧行都认定为明确未送达。

这里保证的是成功进入新转发队列后的持久保留。微信协议尚未收到的内容、入队前的路由创建失败或磁盘不可写不在此保证内；WebUI / SDK 中可能仍有原始记录，需按实际数据调查。长期离线或大量永久失败会占用磁盘，应监控 storage 容量，勿直接删除仍有待发记录的数据库。

## 离线验证

`test/telegram-outbox.test.cjs` 与 `test/telegram-send-lanes.test.cjs` 使用临时数据库、合成消息及本机 HTTP 服务，验证：超过重试上限 / 旧 TTL 后恢复、重启状态、媒体保存、去重、账号隔离、分片续传、429 等待、独立发送通道和真实连接拒绝后恢复。没有调用真实微信或 Telegram。
