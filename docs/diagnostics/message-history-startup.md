# 消息历史 500 与联系人初始化异常排查（未发布修复）

## 已确认原因

### 历史接口返回 `serverError`

SSE 的连接级 TEMP 触发器将变更写入 `message_changes(wxId,id)`。`importHistory` 使用 `INSERT ... ON CONFLICT DO UPDATE` 合并已有消息；当其修改 `bodyFormat` 等字段时，UPDATE 触发器会先记录 OLD，再记录 NEW。这两个引用通常具有同一个主键。

原触发器依赖 `INSERT OR IGNORE` 去重，但 SQLite UPSERT 的 DO UPDATE 分支采用 ABORT 冲突策略，触发器内的 IGNORE 不能防止此次主键冲突，导致整个历史合并语句失败：

```text
SQLITE_CONSTRAINT: UNIQUE constraint failed: message_changes.wxId, message_changes.id
```

HTTP 层原先只返回 `{error:"serverError"}`，未记录异常，因此容器日志无法定位它。状态接口不执行这次历史合并，仍可能显示各服务在线。

修复在插入通知前通过 `NOT EXISTS` 排除已有键，覆盖消息、撤回记录及未匹配撤回的刷新标记。保留通知边界、原写入原子性与无变化时不通知的行为。无需修改持久化数据库结构；TEMP 表和触发器在连接启动时创建。

### SDK 联系人异常刷屏

`wx2tg-puppet` 的 `fetchAllContacts` 在同步 `forEach` 中调用异步联系人 / 群详情查询，既不等待也不捕获其拒绝。SDK 对缺失或不匹配的联系人详情严格报错后，这些拒绝逃逸到进程级异常处理。

SDK 本地修复为每页最多四个并发任务，等待本页结束再取下一页，失败逐项隔离，输出成功 / 失败数量，不打印联系人 ID 或原始接口数据。保留联系人严格校验：失败项不会被伪造为成功，亦不因此删除缓存。该改动不保证服务端能提供原本缺失的联系人详情。

### 启动后暂时无回应

现场日志显示 Telegram 首次 `getMe` 请求发生 `socket hang up`，随后现有重试成功；状态与实际转发记录均表明连接后来恢复。这与历史接口的 SQLite 故障是两件事。

Bot 增加连接尝试开始时的日志，明确 WebUI 启动不等于 Telegram 已上线。没有修改现场代理或账户配置。

## 验证与边界

- 在独立诊断进程中，以 READONLY 模式连接现场数据库；把消息复制到 RAM 中，再执行实际历史适配器。所有历史合并 / 富化写入仅发生在 RAM。
- 原代码复现上述约束错误；修复后目标公众号及现有绑定群聊共 15 个会话、244 条返回记录通过。没有修改运行中的服务或磁盘数据库。
- 诊断进程隔离发送、网络及账户协作者；这一验证不等于完整 Telegram / 微信业务验收。
- 新增真实 HTTP → 消息适配器 → TypeORM / SQLite 回归，覆盖群聊和公众号的已有消息合并。
- 新增 UPSERT / 显式 ABORT 冲突策略下消息与撤回通知的回归。
- 新增异常日志测试，确保日志含错误类别、可用源码位置，不含请求查询参数、Token、SQL 参数或聊天正文。
- Bot 472 项测试及三组浏览器回归通过；SDK 183 项测试通过。

## 为什么原测试漏掉了

旧通知测试仅重放完全相同的历史记录，没有触发实际字段更新；浏览器测试使用模拟历史适配器，未走历史合并 SQL。SDK 初始化也缺少针对异步详情拒绝、并发上限与完成时序的回归。新测试覆盖了这些实际执行路径。
